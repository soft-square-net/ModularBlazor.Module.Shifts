# ModularBlazor.Module.Shifts

[العربية](README.ar.md)

Shifts: newsroom sections and units, the rota (roles defined per tenant or unit), shift templates, attendance (check-in, the shift clock, handover) and integration events; a check-in becomes time-windowed grants. It is a module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform) platform, released on its own as the bundle `shifts`.

> **Status: moved in.** The code moved here from the platform repo and builds against the platform packages.
> Nothing here is packed as a bundle yet: build it and upload the entry project's output in the admin area.

runtime module: see [docs/clean-architecture.md](docs/clean-architecture.md) for the layers, the dependency rules, how
the rota becomes grants, and where a new feature goes.


## How it builds and ships

- It compiles against the platform's contract packages (`WebApi.Contracts`, `ModularBlazor.Abstractions`, ...) from the
  soft-square-net GitHub Packages feed. It never references platform source.
- CI packs one bundle per release: `<module>-<version>.modpkg`, a zip with `module.json`, `server/`, `client/` and
  `contracts/`. The platform's admin area installs it: server part first (tenant migrations), then the client part.
- One version for the whole bundle, set once from the git tag. Unchanged parts are skipped on install.
- An API client ships once, inside the bundle that owns the API, as a hidden client module. Modules that call it
  reference its package with `ExcludeAssets="runtime"` and declare a dependency with a version range in `module.json`.

The server part is `WebApi.Modules.Shifts.Web`'s build output, zipped: every server layer plus the private Mediator
and Ardalis.Result. Upload it on Host Modules (`/host-modules`). The client parts are two dlls, uploaded on Client
Modules (`/client-modules`), the API client first:

| Part | File | What it is |
| --- | --- | --- |
| API client | `soft.square.net.WebApi.Modules.Shifts.Client.dll` | the hidden client module `WebApi.Modules.Shifts.Client`: `ShiftsClient` |
| UI | `soft.square.net.Module.Shifts.dll` | the client module `Module.Shifts`, "Shifts Management" (nav entry "Shifts"), with its `shifts.css` embedded |

The UI's pages are built with MudTail's `mud-*` classes (`ModularBlazor.Abstractions`), in English and Arabic
(`i18n/ar.json`; the stylesheet uses logical sides only, so it mirrors right to left). The module adds a "Shifts" menu
group with a link per page.

| Page | What it does |
| --- | --- |
| `/shifts` | the planner: a unit picked from the cached Organization tree and one week of its shifts (and, unless switched off, of the units below it) on the unit's clock; "Shifts without a unit" for sections that have not moved; "New shift" (also per day) and the overdue shifts |
| `/shifts/mine` | my shifts, with check-in and "check me out" |
| `/shifts/{id}` | one shift: the attendance board (status and check-in or check-out per member), role names from `/roles/effective`, the handover card, timings, publish, edit, check out the shift, delete |
| `/shifts/templates` | a unit's templates: create, edit, delete, and clone into a date, with the clone's warnings and a link to the draft |
| `/shifts/roles` | role definitions: list, add, edit, delete. For the 409s it says what to do: a role in use needs an heir (it offers a tenant-wide one), and a refused lead-flag change can be dropped or become a new role. Permissions come from the platform's catalog (typed by hand without `access.grants.manage`) |
| `/shifts/attendance` | a unit's attendance overrides (`GET`/`PUT /units/{id}/attendance`) and the values in force |
| `/shifts/sections` | moved sections, read-only, with their units; the ones still to move are listed apart |
| `/shifts/sections/move` | move sections to Organization: new units under a Department, or links to existing Section units; the report per section; the JSON export (download or copy); resync the units |

**Time zones.** A unit's shifts are shown and typed on the unit's clock: its own time zone, else the nearest unit
above it that has one, else UTC (the page says which). Shifts without a unit use the browser's clock.

**Live.** The pages reload on `shift.changed` (`ILiveChannel`). The shift page and "My shifts" listen on
`shifts:shift:{id}`; the planner on `unit:{id}`, which also covers the units below. Where that topic is refused (it
needs the Organization module) and for shifts without a unit, it listens on each visible shift instead, so a newly
planned shift appears only on Refresh; the same holds for a new assignment on "My shifts". A page takes at most 40
topics. A reload does not discard an open edit form or a half-written handover note. A shift with no unit has no live
scopes, so only users with tenant-wide `shifts.view` hear about it.

## Category sections and departments

Sections are what shifts were planned on before the Organization tree. Since S4 they can no longer be added or
changed (see "Sections after S4" below); the ones that exist keep working. A section has a kind (`SectionKind`, sent
and stored by name):

| Kind | Serves | Categories | Its rota is granted on |
| --- | --- | --- | --- |
| `Category` (the default) | only its own categories (Sport, Politics) | at least one | `category:{id}` for each of them |
| `Department` | every category (Multimedia, SEO) | none | `section:{id}`, the department itself (until the section moves) |

- Plans, rotas, publishing, check-out and the workflow timers work the same for both kinds.
- **Which sections serve category X**: `GET /api/shifts/sections/serving?category=X` (`ShiftsClient.ListServingSectionsAsync`,
  `shifts.view` or `shifts.manage`): the category's own sections first, then every department, each group by name. The
  Content Designer's routing (Elsa) uses it: text goes to the category's section, images to Multimedia, SEO values to
  SEO.
- Lookups (`ShiftsLookups`, served by the host under `/api/shifts/lookups/{name}`, for pickers and other modules'
  server-side checks through `ILookupClient`; any signed-in user of the tenant):
  - `shifts.sections`: every section; key the id, text the name, column and filter `Kind`;
  - `shifts.departments`: only the departments.

  A lookup filters on one entity's own columns and departments have no category rows, so "which sections serve X"
  is the endpoint above, not a lookup.
- Content checks a content's rights against `press:` and `category:` scopes today. For a department's rota to act on
  the contents routed to it, Content adds `section:{SectionId}` to a content's scopes (its phase 2 part). Once the
  section has moved, that scope is no longer written: the unit's `section:{unitId}` takes its place.
- Sections are replaced by Organization units: see the next sections.

## Organization units (Shifts v2, step S1)

Shifts are moving from the module's own sections to the units of the
[Organization](https://github.com/soft-square-net/ModularBlazor.Module.Organization) service
(Org > Sector > Department > Section). The module references `soft.square.net.Organization.Contracts` and
`soft.square.net.Organization.Client` (1.0.0-preview.1, private: copied into its output).

### The unit cache

`unit_cache` keeps the tenant's units as this module last heard of them: id, org, parent, type, path, names, tags,
time zone, categories and version (`GET /api/shifts/units`, `shifts.view`).

- **Events.** The module uses integration events (`UsesIntegrationEvents`, the outbox and inbox in schema `shifts`) and
  subscribes to `org.unit-*.v1` and `org.membership-changed.v1`.
  - Created and updated units are applied by version: a state that is not newer than the cached one (a duplicate, or
    a late event) changes nothing.
  - A move rebases the unit's whole subtree, but only when the move is newer for the unit, so a late move cannot drag
    the subtree back.
  - A removed unit stays as a tombstone: later events for it are ignored.
  - A membership on a unit the cache has never seen makes the module read that unit from the directory, as its service
    client (when one is configured).
- **First fill.** For each tenant, when the module loads, the module reads `IUnitDirectory.ListAsync` from the
  deployment's local Organization API, as its own service client. Without a service client, or when Organization is
  unreachable, it only logs: the tenant still starts.
- **Resync.** `POST /api/shifts/units/resync` (`shifts.manage`) does the same read with the admin's token. It applies the
  listed units by version and drops the cached units the directory no longer lists.

Settings (module settings, section `Shifts:Organization`):

| Setting | Meaning |
| --- | --- |
| `BaseUrl` | The address that serves this deployment's `/api/organization/local/*` (the gateway, or an internal address), for example `https://gateway/`. Empty: the module never calls Organization, and the cache fills from events only. |
| `CentralUrl` | The address of the central management API `/api/organization/*`. Empty: `BaseUrl`. |
| `TokenEndpoint`, `ClientId`, `ClientSecret`, `ClientScope` | The module's service client (client credentials), for the first fill. Put the secret in the host's settings, never in the module defaults. |

### Shifts in units

`Shift.UnitId` sits next to `SectionId`. A new shift (`POST /api/shifts/shifts`) gets its unit as follows:

| The shift's `sectionId` | `unitId` left out | `unitId` given |
| --- | --- | --- |
| Left out | 400: a shift needs a unit or a section | that unit; the shift takes the section mapped to it, if any |
| A section that has not moved | no unit (`UnitId` null, as before) | that unit, which must be cached and not removed (else 400) |
| A section that has moved | the section's unit | the section's unit only (any other is 400) |

`sectionId` is optional since S4. An update that leaves it out keeps the shift's section. An update can give a unit to
a shift that has none, but never moves a shift to another unit.

A published shift's grants are written on these scopes:

- `unit:{id}` (the unit id in its 32-digit form);
- `category:{c}` for each category of the unit (Organization's `CategoriesOf`: the unit's own categories, or those of
  the units below it; the wildcard `*` is skipped);
- `section:{unitId}` for a unit tagged `department` (a department section);
- the section's `category:{c}` scopes, as long as the shift still has its section;
- a department section's `section:{sectionId}` (an integer), **only while the section has not moved**. Once it has a
  unit, `section:{unitId}` replaces it. On upgrade, the shift clock's first tick per tenant rewrites the grants, so
  this takes effect by itself for published shifts that have not ended.

A shift with no unit, or whose unit is not cached or was removed, keeps all of its section's scopes: a shift is never
left without a scope. A department linked to a Section unit that is not tagged `department` gets no `section:` scope
at all once moved; the move's report says so, and tagging the unit in Organization fixes it.

### Moving the sections to Organization

`POST /api/shifts/sections/move-to-organization` (`shifts.manage`) takes `{ "parentUnitId": "<Department unit>" }`.

- **What it does for each section that has not moved yet:**
  - It creates a Section unit under that Department through the central API, with the caller's token. The unit gets
    the section's name (in both languages) and its categories. A department section gets the tag `department` and the
    wildcard category `*` (decision D1).
  - It records `section_unit_map` (section → unit), sets `UnitId` on every shift of the section, and publishes
    `shifts.section-moved.v1` `{ sectionId, unitId }` (subject `section:{sectionId}`, with the unit path and the org id
    on the envelope), all in one save.
  - It rewrites the grants of the section's published shifts that have not ended.
- **Idempotent.** A moved section is reported `AlreadyMapped`. A Section unit with the same name under the parent, left
  by an interrupted run, is reused rather than created again.
- **One result per section:** `Created`, `AlreadyMapped`, `Linked` or `Failed`, with the reason. For example, if
  Organization does not accept `*` yet, the department sections fail with Organization's answer and a note about D1,
  and the other sections still move. Run the move again once that is fixed.
- **By hand**, when this deployment cannot reach the central service:
  1. `GET /api/shifts/sections/export` returns each section with the Section unit to create for it (type, names, tags,
     categories).
  2. Create those units in Organization.
  3. Once the units are in the cache, link them: `{ "links": [{ "sectionId": 1, "unitId": "…" }] }`. Each linked
     section is reported `Linked`.
- **From the UI:** `/shifts/sections/move` does all of this: pick a Department, or a Section unit per section, or
  both; export the JSON; resync the units. Without the central API, pick a unit for every remaining section in one go:
  the API asks for a Department as soon as one section is left without a unit.

## Sections after S4

The section pages that added and changed sections are gone, and so are `POST /api/shifts/sections` and
`PUT /api/shifts/sections/{id}`. What remains: `GET /api/shifts/sections` (each with `movedToUnitId`), `serving`,
`{id}/settings`, `export`, `move-to-organization` and the lookups. No table or column is dropped.

**A tenant that never moved its sections** keeps working:

- its sections and section-only shifts stay readable, and those shifts can be published, checked in and checked out;
- it can **still plan new shifts without a unit** on an existing section (`sectionId` without `unitId`; on the planner,
  "Shifts without a unit");
- those shifts keep the section's scopes, `section:{sectionId}` included, exactly as before;
- the move, the manual links and the JSON export stay available, from the UI and the API;
- what it loses: it can no longer add a section, or change a section's name, kind, categories or timing overrides.
  To change what a rota may act on, move the section and edit the unit in Organization.

A new tenant has no sections, so it needs the Organization module to plan shifts.

## Roles, templates and unit authority (Shifts v2, step S2)

### Role definitions

The rota's roles are rows now (`shift_roles`), not an enum: `ShiftRoleDefinition` has a `key` (a slug: lowercase
letters, digits and dashes), `nameEn`, `nameAr`, `permissions`, `isLead` and `unitId` (null: tenant-wide).

- **Which definition holds.** For each key, the definition of the nearest unit up the shift's unit path wins, else the
  tenant-wide one. A shift with no unit (or whose unit is not cached) sees the tenant-wide definitions only. A unit can
  add roles of its own (`photo-editor` for one Department) or override a tenant role (Sport's own `desk`).
- **Seeding.** A tenant with no definitions at all gets `manager` (lead), `desk` and `editor`, with the permissions the
  old roles had (`ShiftRolesInitializer`, on every module load; an empty table only).
- **The rota** sends `roleKey` per member. The old names still work (`Manager` is read as `manager`). The member keeps
  the role's lead flag (`isLead`): a Draft may have no lead, there is never more than one, and publishing (and every
  change to a published shift) needs exactly one.
- **Permissions** must be in the platform's permission catalog (any installed module's, or the platform's own); else 400.
- **Changes.** A permissions change rewrites the grants of the published shifts that have not ended and use the
  definition. The lead flag cannot change while such shifts or templates use it (409). A definition in use is deleted
  only when another of the same key and lead flag takes over (a parent unit's, or the tenant's), else 409.
- **Migration.** `RolesAndTemplates` turns each rota row's `Role` into `RoleKey` (`LOWER(Role)`) and `IsLead`
  (`Role = 'Manager'`). Its Down restores the names and deletes the shifts that have no section.

| Endpoint | Permission | What it does |
| --- | --- | --- |
| `GET /api/shifts/roles` | `shifts.view` or `shifts.manage` | every definition of the tenant |
| `GET /api/shifts/roles/effective?unitId=` | `shifts.view` or `shifts.manage` | the definitions that hold for a unit (none: tenant-wide); for the rota editor |
| `POST /api/shifts/roles` | `shifts.manage` on the unit (tenant-wide for a tenant role) | add one; a key is unique per unit (409) |
| `PUT /api/shifts/roles/{id}` | as above, on the definition's unit | names, permissions, lead flag |
| `DELETE /api/shifts/roles/{id}` | as above | remove one |

### Templates

`ShiftTemplate` (`shift_templates`) is a unit's recurring shift: `name`, `startLocal` (a wall-clock time), `duration`
(elapsed time, at most 24 hours), `slots` (role key and count, one per role) and `defaultMembers` (user and role key).
Its roles must hold for the unit and its default members must be members of it (see below), when it is saved.

`POST /api/shifts/templates/{id}/clone` `{ "date": "2026-03-29" }` makes a **Draft** shift on that date, returned with
`warnings`:

- **Time zone.** The start is `date` + `startLocal` in the unit's time zone (else the nearest unit above it that has one,
  else UTC, with a warning); the end is the start plus `duration`, so a night across a DST change lasts its duration
  and ends an hour earlier or later on the clock. A start the clocks skip moves forward by the gap (02:30 on the day
  the clocks go forward is 03:30); a start the clocks pass twice is the first one.
- **Rota.** The default members whose role still holds and who are still members on that day, with one lead at most;
  everyone left out is a warning, and so is every slot that is not filled and a shift with no lead.
- **Section.** The section mapped to the unit, if any; else the shift has a unit and no section (`sectionId` null).

| Endpoint | Permission |
| --- | --- |
| `GET /api/shifts/templates?unitId=`, `GET /api/shifts/templates/{id}` | `shifts.view` or `shifts.manage` |
| `POST /api/shifts/templates`, `PUT …/{id}`, `DELETE …/{id}`, `POST …/{id}/clone` | `shifts.manage` on the template's unit |

### Who may plan a unit's shifts

- **Authority.** `shifts.manage` is checked on the unit's scopes, `UnitScopes.For(path)`: a grant on a Department covers
  its Sections. Adding, changing, publishing, checking out and deleting a unit's shift all check it. A shift with no
  unit, sections, the move to Organization and the units resync need `shifts.manage` tenant-wide. A service client that
  checks shifts out (the workflow) needs it tenant-wide too.
- **Rota members (D6).** Everyone on a unit's rota must be a member of the unit or of a unit above it (Organization's
  `MembersOf`, read with the caller's token) at the shift's start, with an identity (`subject`, matched against the
  rota's user id). Without Organization configured, or when it does not answer, the change is refused with 503. A
  shift with no unit skips the check.
- **Grants** carry the permissions of the role definitions; since S3 they come from check-in (see below).

## Attendance, the shift clock and events (Shifts v2, step S3)

### Check-in and status

Every rota row has `checkedInAt`, `checkedOutAt` and `absentAt` (plus who did it, and whether the check-out was
automatic). Its `status` is derived from them and the thresholds:

| Status | When |
| --- | --- |
| `expected` | not checked in, not (yet) marked absent |
| `present` | checked in by the start plus the late threshold |
| `late` | checked in after the start plus the late threshold |
| `absent` | not checked in by the start plus the absent threshold (the clock marks it) |
| `left-early` | checked out by hand before the end |
| `overtime` | checked out by hand, or still in, after the end plus the overtime threshold |

- **Who.** A member checks themselves in (`POST /shifts/{id}/check-in`); the shift's lead or a manager (`shifts.manage`
  on the unit) checks someone else in (`POST /shifts/{id}/members/{userId}/check-in`). Check-in needs a published shift
  that has not ended, from the start minus the early threshold until the end. A member who checked out may check in
  again before the end.
- **Grants come only from check-in.** Publishing no longer gives the rota its rights: a member's grants
  (`ReplaceSourceAsync("shift:{id}")`) run from `checkedInAt` to `checkedOutAt`, else to the end plus the check-out
  grace. A check-out rewrites the source at once, so the host's live hub drops the member's shift topics. When the
  module starts, the clock's first tick per tenant rewrites the grants of every published shift that has not ended, so
  members who have not checked in lose the rights an older version wrote at publish.
- **Thresholds (D5).** Module settings, overridable per unit: `EarlyCheckIn` 00:30, `LateAfter` 00:10, `AbsentAfter`
  01:00, `OvertimeAfter` 00:15, and the existing `CheckoutGrace` 00:15. A shift takes each value from the nearest unit
  up its path that sets it (`unit_attendance`), then (grace only) its section's grace, then the module setting.
  `GET /units/{id}/attendance` shows a unit's overrides and what holds; `PUT` sets them (minutes, 0 to 1440, null to
  inherit; `shifts.manage` on the unit) and rewrites the grants of the unit's shifts that have not ended.

### The shift clock

`ShiftClock` is a hosted service. Every `ClockInterval` (1 minute) it takes each active tenant whose module database
is ready, takes the tenant database's try-lock `shifts:clock` (one pool instance per tenant does the work, the others
skip it), and in a tenant scope:

1. marks absences: members not checked in at the start plus the absent threshold (`absentAt` = that time);
2. at the end plus the grace, checks everyone still in out automatically (at the end plus the grace) and ends the
   shift: `checkedOutAt` = the end plus the grace (when the grants end), `endedAt` = the tick, `endedBy` =
   `shifts:clock`; it publishes `shifts.checked-out.v1` per member and `shifts.ended.v1`.

Every step looks at state, not at time passed since the last tick, so a tick that runs twice (or late) does nothing
more. A shift checked out by hand (the lead, a manager or the workflow) is ended then, with `endedBy` the caller.

### Handover

The lead writes `handoverNote` (1 to 4000 characters) with `PUT /shifts/{id}/handover` `{ "note": "…" }`, on a
published shift that has started; it is published as `shifts.handover.v1`.

### Ended shifts

`GET /shifts/ended?since={utc}&take=` (`shifts.manage`) lists the shifts that ended at or after `since`, ordered by
`endedAt` (then id): `id`, `unitId`, `sectionId`, `startsAt`, `endsAt`, `endedAt`, `endedBy` (`shifts:clock` or a user
id) and `checkedOutAt`. `take` is 200 by default, at most 500: poll with the last `endedAt` you saw. `/overdue` is
unchanged.

### Events (`Shifts.Contracts`)

The module writes integration events to its outbox (saved with the change that caused them). The package
`soft.square.net.Shifts.Contracts` (`src/Shifts.Contracts`, packed by `.github/workflows/packages.yml`, pushed on a
`v*` tag) has the types, the records and `ShiftsLive`. The envelope's source is `shifts`, its subject `shift:{id}`
(`section:{id}` for a section move), with the unit's path and the organisation id.

| Type | Data | When |
| --- | --- | --- |
| `shifts.published.v1` | `ShiftPublished(shift)` | first publish |
| `shifts.updated.v1` | `ShiftUpdated(shift)` | a change to a published shift |
| `shifts.cancelled.v1` | `ShiftCancelled(shift, by, at)` | a published shift is deleted |
| `shifts.member-added.v1` | `ShiftMemberAdded(shiftId, unitId, userId, roleKey, isLead)` | a rota row added to a published shift |
| `shifts.member-removed.v1` | `ShiftMemberRemoved(…same…)` | a rota row removed from a published shift |
| `shifts.checked-in.v1` | `ShiftCheckedIn(shiftId, unitId, userId, roleKeys, at, by, status)` | a check-in |
| `shifts.checked-out.v1` | `ShiftCheckedOut(shiftId, unitId, userId, at, by, automatic, status)` | a member's check-out (by hand, with the shift, or by the clock) |
| `shifts.handover.v1` | `ShiftHandover(shiftId, unitId, note, by, at)` | the lead writes the note |
| `shifts.ended.v1` | `ShiftEnded(shift, by, at)` | the shift is checked out, by hand or by the clock |
| `shifts.section-moved.v1` | `SectionMoved(sectionId, unitId)` | a section moved to an Organization unit |

`shift` is a `ShiftSnapshot`: `shiftId`, `unitId`, `unitPath`, `sectionId`, `startsAt`, `endsAt`, `published`,
`endedAt`, `handoverNote` and `members` (`userId`, `roleKey`, `isLead`, `checkedInAt`, `checkedOutAt`, `absentAt`,
`status`). An absence has no event of its own: it is in the ended snapshot.

### Live

Every change sends `shift.changed` `{ shiftId }` on the topic `shifts:shift:{id}` and to the shift's unit
(`PublishToUnitAsync(unitPath, …)`). The manifest declares the topic kind `shift` (`shifts.view`); its scope resolver
gives the scopes of the shift's unit, so a grant on a Department covers its Sections' shifts.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform          git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.Shifts     this repo
```

(another location: `-p:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080, client
5070), so stop the Hybird lab, and any other module's playground, first. It has two launch profiles:

| Profile | What it does | Use it for |
| --- | --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.Shifts.Web/bin/<Configuration>/net10.0` (`Modules:Local`, Development only), and its client parts from their build output (`ClientModules:Local`): installed and active on start | Daily work: change code, rebuild, restart the `webapi` resource in the dashboard (or F5 again) |
| `install` | The platform starts without the module, as in production; every build zips the module to `playground/out/shifts.zip` and copies the client parts to `playground/out/client` | Before a release: upload the zip on http://localhost:5070/host-modules (sign in as the dev platform admin, `admin@modular.local`) and activate it, then the two dlls on `/client-modules`, which runs the real install path |

```bash
dotnet run --project playground --launch-profile dev
```

```bash
dotnet run --project playground --launch-profile install
```

Open http://localhost:5070/shifts and sign in with the organisation `acme` and one of its dev accounts below. Or try
the API in Scalar, http://localhost:5080/scalar, document `shifts`: sign in there with the organisation `acme` and
one of its dev accounts (the passwords are in the platform's `WebApi.Identity.Server/appsettings.Development.json`),
and send the header `X-Tenant: acme`.

| Account | Shifts permissions in `acme` (given by the playground) |
| --- | --- |
| `acme-admin@modular.local` | `shifts.*`: planning, publishing, templates, roles, moving sections, checking any shift out |
| `editor@modular.local` | `shifts.view`: sees sections and shifts; checks themselves out of a shift they are on |

Units come from Organization, which the playground does not run. Planning a unit's shift with a rota needs
`Shifts:Organization:BaseUrl` for the rota check (without it: 503), and a fresh playground has no sections, so
planning needs Organization or a stand-in that serves `/api/organization/local/*`.

A member who checks in to a published shift gets `content.*` grants (accept, assign, review, publish, ...) on the
shift's scopes until they check out; they matter once the Content module is installed next to this one.

In Development the platform seeds the dev tenants `acme` and `globex` on the playground's server. The playground gives
the module's permissions to the dev accounts above through the WebApi's `Access:DevGrants` (Development only, by
email): the first time each account calls the API in `acme`, it gets them as ordinary grants with the source `dev`.
Data stays in the Docker volume `shifts-playground-data` and in `playground/.data` (the module catalogs); delete both
to start over.

The playground is not in `ModularBlazor.Module.Shifts.slnx`: CI builds the module without a platform checkout.

Trunk-based: `main` always produces an installable bundle; short-lived `feat/...` and `fix/...` branches; a release
is a tag such as `v1.2.0`.
